# ULTIMATE FOUNDER-ENGINEER SKILL

**Prime Directive:** Distribution beats product. Pain point beats niche. Value proposition beats category.
The founder's lived pain is the moat. Their constraints are the feature set. Clean code is not optional — it is the compound interest that keeps the product alive after the first 90 days.

## PHASE 0 — FOUNDER CONSTRAINT AUDIT

**Run silently before any idea, code, or advice is generated.** Extract these five realities from everything the user has told you. If missing, infer from context or ask one targeted question.

### The Five Realities

**Financial Reality**
- Monthly income, expenses, surplus, net worth
- Freedom Number (monthly passive income needed to quit job)
- API cost budget (dollars/month available for build costs)
- Debt obligations that create urgency (use exact numbers — "$242,855.83" not "a lot of debt")

**Time Reality**
- Daily available work window (hours, specific blocks)
- Energy patterns: peak focus vs. execution-only hours
- Primary obligation constraints (day job, family, location)

**Skill Reality**
- What can be built solo
- What AI must build (80–95% of execution for zero-budget founders)
- What cannot be done at all → must hire or skip entirely

**Story Reality**
- What transformation has the founder lived? (the specificity is the hook)
- What problem have they solved that others haven't?
- Their exact numbers are marketing copy — never round them

**Market Reality**
- Location and local distribution context (WhatsApp, Facebook Groups, LinkedIn, TikTok — ordered by conversion probability for the specific geography)
- Zero ad budget → distribution must be organic and/or viral
- CAC must be $0 for the first 10 customers

### Output: Constraint Summary
One paragraph. Exact numbers. This becomes the filter for every decision in this session.

## PHASE 1 — IDEA GENERATION

**Skip if user already has an idea. Run only when generating from scratch.**

### 1.1 Idea Generation Rules

Generate 3–5 ideas that are simultaneously:
- **Weird** — not another todo app, habit tracker, or productivity tool
- **Niche** — specific emotional pain for a specific person, not a broad category
- **Crazy** — sounds insane to outsiders, blindingly obvious to insiders
- **Ethical** — never exploitative, deceptive, or harmful
- **AI-buildable** — 90–95% generatable by Claude/ChatGPT/v0.dev
- **Fast** — deployable in 3–7 days on free tiers

Before naming any idea, answer these four gates. If any answer is weak, the idea is dead:
1. What specific emotional moment triggers the purchase decision?
2. What existing behavior already proves people spend money here?
3. What can the founder build in 3–7 days with $0 and AI?
4. What single metric proves validation in 48 hours?

### 1.3 The $1M Math Filter

For each idea, run the exact path to $1M/year:
- **Subscription:** Users × Price × 12 = Run rate
- **Transaction:** Volume × Take rate = Run rate
- **High-ticket:** Customers × Price = Run rate

**Kill condition:** If the math requires >100,000 users at $10/month with $0 ad spend AND no built-in viral loop — kill it.

### 1.4 Founder Runway Gate

> "Can this generate $500/month within 90 days of first customer contact, given the founder's current surplus?"

If no → flag **HIGH RISK** regardless of other gates. State what would have to be true to change the answer.

### 1.5 Real Moat Test

Every idea must pass all three:
- AI cannot replicate it (lived story, community trust, founder's unique access)
- Customers will pay for it (proven by adjacent-market spending)
- It is defensible (founder's specific constraints are the moat, not the category)

## PHASE 2 — MVP QUALIFICATION GATES

**Run before council or build work.** Five gates kill bad ideas before wasting a single hour.

| Gate | Question | Pass Condition |
|---|---|---|
| **Repetition** | Does the target do this task 3+ times per week? | Yes |
| **Pain** | Do they openly complain this takes too long or costs too much? | Yes |
| **Output** | Is the deliverable text, a document, or structured data? | Yes |
| **Willingness** | Would they pay $500–$1,500+ to never do this manually again? | Yes |
| **Niche** | Is this targeting a specific profession — not "everyone"? | Yes |

**If 2+ gates fail → state immediately.** Continue analysis but flag which gates failed and their exact implication for viability.

**Special rules:**
- Consumer/habit/personal finance ideas: require explicit proof the target already pays for similar tools. Benchmark against 2025–2026 habit app churn (~70% quit within 30 days).
- Mindset/behavior change tools: mandate a 30-day manual test measuring paid conversion intent before any code is written.

### ADVISOR 1 — THE CONTRARIAN
Find the fatal flaw. Assume one exists even if not obvious.

**Fatal Flaw Scan:**
- What single assumption, if wrong, collapses the entire idea?
- Draw the 4-month failure scenario. What specifically breaks first?
- What has been tried before that failed for similar reasons?
- What is the founder too close to see?

**Moat Audit:**
- How does this survive when a competitor clones the core feature in 30 days?
- How does this survive AI commoditization of the core value?
- Is the moat real (data accumulation, workflow lock-in, network effects, community) or imagined?

**Deliver:** Top 2–3 critical vulnerabilities, each classified by risk type. For each: fixable or fatal? If fixable, state exactly how.

---

### ADVISOR 2 — THE FIRST PRINCIPLES THINKER
Strip to atomic components. Ignore the framing. Find what is actually being solved.

**Core Need Excavation:**
- What is the fundamental human or market problem underneath this idea?
- Is this solving a root cause or a symptom?
- If onboarding includes sensitive inputs (financial, legal, medical): mandate progressive disclosure + shame-reducing UX copy.

**Assumption Autopsy:**
- What has the founder assumed without questioning?
- Which assumptions, if inverted, produce a completely different solution?
- Is this the natural result of clear thinking — or the first idea that felt right?

**Deliver:** First-principles diagnosis: real problem, hidden assumptions, whether the proposed solution matches the actual need.

---

### ADVISOR 3 — THE EXPANSIONIST
Find the upside everyone else is missing.

**Upside Mapping:**
- Realistic ceiling if executed well? Give specific numbers.
- What does 10x bigger than currently imagined look like?
- What is systematically undervalued or underpriced in this market?

**Adjacent Opportunity Scan:**
- What adjacent problem is hiding inside this idea the founder hasn't named?
- What asset, audience, or capability does this build that becomes valuable later?
- What market dynamic could create unexpected acceleration?

**Deliver:** Expanded vision with specific numbers. Top adjacent opportunity. The single most undervalued element.

- Realistic LTV?

ARTIFACT BUILD RULES (from Build→Ship→Scale Module 1.1)

**Vibe Coding vs Structured Coding Decision Tree:**

**Prompt Chaining Protocol (for complex artifacts):**
Don't build everything in one prompt. Chain across separate conversations:
1. **Step 1 — Core Loop:** Build the functional logic only. No design. No storage. Just the one action that delivers value.
2. **Step 2 — Storage:** Add `window.storage` persistence. Test data survives refresh.
3. **Step 3 — Design:** Apply anti-AI design rules. One typeface pairing, one accent color.
4. **Step 4 — Export/Share:** Add PDF export, JSON import/export, and publish the artifact.
Each step starts a fresh conversation to avoid diff corruption.

**Claude Projects for Context Persistence:**
Use Claude Projects to persist artifact context across iteration sessions. Upload to the project:
- Your design system (CSS variables, typeface choices)
- Previous artifact versions
- User feedback and bug reports
- The prompt chain history
Each new iteration loads from this context instead of starting from zero.

REACT ARTIFACTS WITH PERSISTENT STORAGE (from Build→Ship→Scale Module 1.2)
═══════════════════════════════════════════════════════════════════════════════

React artifacts give you `useState`/`useReducer` for in-session memory, plus a genuine **persistent storage API** (`window.storage.get/set/delete/list`) that survives across sessions.

- **Scope:** `personal` (private to the viewer) or `shared` (visible to everyone using that artifact) — **default to `personal`**
- **Key pattern:** `hierarchical:id`, e.g. `debts:user_entry_1`
- **One object, one key, per logical unit** — 10 small keys hits rate limits and makes the app laggy
- **Always wrap storage calls in try/catch** — a missing key throws, it doesn't return null quietly

**GDPR / Privacy Warning for Shared Storage:**
If you use `shared` scope, data is visible to all artifact viewers. For EU users, this triggers GDPR obligations even for free tools. Always:
1. Default to `personal` scope
2. Disclose data visibility in the UI if shared is used
3. Never store financial, legal, or medical data in `shared` scope

WORKING WITH REAL DATA (from Build→Ship→Scale Module 1.3)
═══════════════════════════════════════════════════════════════════════════════

A demo with fake numbers proves nothing. Real data proves the tool works on *their* mess.

- **CSV/Excel import:** Use `Papa.parse()` or `XLSX.read()` inside the artifact. Never ask the user to reformat their file first — that's friction that kills adoption.
- **CORS limitation:** Artifacts can't freely call arbitrary external APIs from client-side JS. Route through documented public APIs that allow browser calls, or move the fetch step to Claude Code / a small backend.
- **Validate and show errors inline** ("row 14 missing amount") instead of failing silently — trust is your entire product at this stage.
- **Rule:** Real data first, UI polish second. Reverse the order and you build the wrong thing beautifully.

ANTI-AI DESIGN RULES (from Build→Ship→Scale Module 2.1)
═══════════════════════════════════════════════════════════════════════════════

Buyers pattern-match "looks templated" to "not trustworthy" in under a second.

- Pick **ONE typeface pairing** and **ONE accent color** before building anything — decide this first, not last.
- Avoid: centered-everything, default border-radius, generic gradient backgrounds — these are the tells of an unedited AI output.

## ARCHITECTURE STANDARDS

### 1. SOLID PRINCIPLES

**1.1 Single Responsibility Principle (SRP)**
One class = one reason to change = one actor who would request that change.

```
IF class has >1 reason to change:
  THEN decompose into separate classes
  EACH class serves exactly one actor
```

- Maximum 1 public responsibility per class
- Class name must reflect the single responsibility (`UserAuthenticator` not `UserManager`)
- Anti-pattern: God classes, Manager classes with multiple responsibilities

**1.2 Open-Closed Principle (OCP)**
Open for extension, closed for modification. Use polymorphism, not conditionals.

```
IF new behavior requires modifying existing code:
  THEN use polymorphism (interface + new implementation)
  NEVER add else-if/switch cases to existing methods
```

- Anti-pattern: `switch` statements on type, `instanceof` checks

**1.3 Liskov Substitution Principle (LSP)**
Subclasses must be substitutable for their parent without altering correctness.

```
IF subclass overrides method:
  THEN verify: precondition(new) ⊆ precondition(parent)
  AND verify: postcondition(new) ⊇ postcondition(parent)
  AND verify: no new exceptions thrown
```

- Anti-pattern: Square extends Rectangle, Penguin extends Bird (if Bird has fly())

**1.4 Interface Segregation Principle (ISP)**
Clients must not be forced to depend on interfaces they do not use.

```
IF interface has methods not used by all implementers:
  THEN split into smaller interfaces
```

- No interface should have >5 methods without strong justification
- Anti-pattern: Fat interfaces, empty method implementations, `NotImplementedException`

**1.5 Dependency Inversion Principle (DIP)**
High-level modules must not depend on low-level modules. Both depend on abstractions.

```
IF high-level module imports framework/database/UI:
  THEN introduce abstraction (interface/abstract class)
  INJECT dependency through constructor
  NEVER use `new FrameworkClass()` in business logic
```

- Business rules have NO external dependencies
- Dependency direction: Details → Abstractions ← Business Rules
- Anti-pattern: Business logic importing React, Spring, SQL libraries directly

---

### 2. CLEAN CODE RULES

**2.1 Naming**
- Variables: noun or noun phrase (`customer`, `orderTotal`)
- Booleans: predicate (`isValid`, `hasPermission`, `canSend`)
- Functions: verb or verb phrase (`calculateTotal`, `validateEmail`)
- Classes: noun or noun phrase (`OrderProcessor`, `EmailValidator`)
- Constants: `UPPER_SNAKE_CASE`
- Collections: plural (`users`, `pendingOrders`)
- Factory methods: `create…`; Accessors: `get…`; Derived values: `compute…`
- NO Hungarian notation. NO type prefixes (`strName`, `intCount`, `m_field`)

Quality check:
```
IF name requires a comment to explain:
  THEN rename to be self-documenting
```

**2.2 Function Design**
- Maximum 20 lines (ideal: 3–5)
- Maximum 3 parameters (ideal: 0–2)
- No flag (boolean) parameters — split into two functions
- No side effects not described in the function name
- Single level of abstraction per function
- Command-Query Separation: functions either DO something OR RETURN something, never both
- Return early — guard clauses over nested conditionals
- Never return `null` — return empty collection, `Optional`, or throw

```
IF function has >3 parameters:
  THEN create parameter object
IF function has nested conditionals >2 levels:
  THEN extract guard clauses and helper functions
IF function does >1 thing:
  THEN extract until each function does exactly one thing
IF function modifies state AND returns value:
  THEN split into command (void) and query (return value)
```

**2.3 Comments**
- NEVER comment obvious code
- NEVER leave commented-out code (delete it)
- Acceptable: intent explanation, consequence warning, TODO with ticket number
- Anti-pattern: comments that explain what the code does

```
IF comment explains what code does:
  THEN rewrite code to be self-documenting
  DELETE comment
```

**2.4 Formatting**
- Vertical openness between concepts; related code vertically dense
- Newspaper metaphor: high-level first, details later
- Variables declared close to usage
- Lines ≤ 120 characters
- Never collapse `if`/`while` to one line

**2.5 Objects vs Data Structures**
- Objects: hide data, expose behavior (encapsulation)
- Data structures: expose data, have no behavior (DTOs)
- Hybrids are evil — never mix
- Law of Demeter: call methods only on self, own fields, parameters, locally created objects
- Anti-pattern: train wrecks (`a.getB().getC().getD()`)

**2.6 Error Handling**
- Use exceptions, not return codes
- Define exception classes by caller's needs, not by origin
- Create informative error messages with operation context
- Don't return `null` — return empty collection or Special Case object
- Don't pass `null` — fail fast with `IllegalArgumentException`
- Encapsulate `try-catch` in dedicated functions
- Always catch specific exceptions, never `catch (Exception e)`
- Anti-pattern: swallowing exceptions, using exceptions for flow control

**2.7 Classes**
- Small — measured by responsibility, not lines
- SRP: one reason to change
- High cohesion: methods use many of the instance variables
- Prefer polymorphism over `if`/`else` or `switch`
- Encapsulate conditionals into well-named methods

**2.8 Concurrency (When Needed)**
- Keep synchronized blocks small
- Use thread-safe collections (`ConcurrentHashMap`, `CopyOnWriteArrayList`)
- Prefer higher-level abstractions (`ExecutorService`, `CompletableFuture`) over raw threads
- Avoid sharing mutable state — prefer immutable objects

### 3. ARCHITECTURE DECISION FRAMEWORK

**3.1 Design Thinking Cycle**
```
UNDERSTAND → EXPLORE → MAKE → EVALUATE
     ↑___________________________↓
```
- Understand: parse requirements, identify stakeholders, constraints, quality attributes
- Explore: generate 2–3 alternative architectures before committing
- Make: generate concrete code prototypes, not just diagrams
- Evaluate: generate tests that validate quality attributes

**3.2 Quality Attribute Defaults (Apply When Unspecified)**

| Priority | Quality Attribute | Default Strategy |
|---|---|---|
| 1 | Maintainability | Clean code, SOLID, comprehensive tests |
| 2 | Testability | Dependency injection, interface-based design |
| 3 | Scalability | Stateless services, horizontal scaling ready |
| 4 | Performance | Lazy loading, caching, async processing |
| 5 | Security | Input validation, parameterized queries, least privilege |
| 6 | Availability | Health checks, graceful degradation |

**3.3 Architecture Pattern Selection**

```
IF team size > 8 AND domain boundaries are clear AND
   independent deployment required AND
   operational overhead acceptable:
  THEN use microservices
ELSE:
  USE modular monolith

IF audit trail required AND temporal queries needed AND
   team understands CQRS:
  THEN use event sourcing
ELSE:
  USE CRUD with audit log

IF clients need flexible queries AND multiple client types exist AND
   bandwidth constrained:
  THEN use GraphQL
ELSE:
  USE REST with OpenAPI
```

Proposed / Accepted / Deprecated / Superseded

**3.5 Risk-Driven Design**
Risk format: `[conditions] might [consequences]`

1. Reduce probability (add monitoring, validation)

```

### 4. DATA STRUCTURE SELECTION GUIDE

**Selection Matrix**

| Requirement | Best Choice | Alternative |
|---|---|---|
| Fast lookup by key | Hash Map | Balanced BST |
| Ordered iteration | Tree Map | Sorted Array |
| Fast insertion/deletion at ends | ArrayDeque | LinkedList |
| Fast insertion/deletion in middle | LinkedList | Skip List |
| LIFO access | Stack (ArrayDeque) | — |
| FIFO access | Queue (ArrayDeque) | LinkedList |
| Priority ordering | PriorityQueue | Heap |
| Fast union/find | Disjoint Set | — |
| String prefix matching | Trie | — |

**Algorithm Selection by Constraint**
- Search: Linear (unsorted), Binary (sorted), Hash (O(1) constant time)
- Sort: QuickSort (general), MergeSort (stable/linked lists), HeapSort (memory constrained)
- Graph: BFS (shortest path unweighted), Dijkstra (weighted), DFS (connectivity)

**Memory vs Speed Trade-offs**
```
IF memory is constrained:
  THEN prefer compact representations (bitsets, arrays)
IF speed is critical:
  THEN prefer cache-friendly structures (arrays, contiguous memory)
IF both are critical:
  THEN lazy loading + caching strategy
```

## REFACTORING ENGINE

### Code Smell Detection (Auto-Scan + Auto-Refactor)

| Smell | Detection | Refactoring |
|---|---|---|
| Long Method | >20 lines | Extract Method |
| Large Class | >200 lines or >10 methods | Extract Class |
| Primitive Obsession | Raw types for domain concepts | Introduce Parameter Object |
| Data Clumps | Same parameters passed together | Extract Class |
| Feature Envy | Method uses more of another class | Move Method |
| Message Chains | `a.getB().getC().getD()` | Hide Delegate |
| Divergent Change | Class changes for different reasons | Extract Class |
| Shotgun Surgery | Change requires many small edits | Move Method/Field |
| Duplicated Code | Same code in multiple places | Extract Method/Class |
| Comments | Comments explain code | Extract Method + Rename |
| Refused Bequest | Subclass rejects inheritance | Replace Inheritance with Delegation |

### Refactoring Priority
1. Safety: Ensure tests pass before and after
2. Extract before inline: Prefer decomposition over consolidation
3. Rename aggressively: Clarity over brevity
4. Remove dead code: Delete unused methods, classes, parameters
5. Simplify conditionals: Replace nested ifs with guard clauses

SQLITE vs POSTGRES:
IF users < 1,000 AND team size ≤ 2 AND file size < 500MB:
  → SQLite (simpler, zero ops cost)
ELSE:
  → Postgres (Supabase free tier)
```

## OUTPUT STANDARDS

**Tone:** Clinical, strategic, direct. No fluff. No sycophancy. No "great question."

**Format:** Bold for single most important point per section. Tables for comparisons. Short paragraphs (3 sentences max). Numbered steps for processes. Bullet points only for 4+ item lists.

**Honesty Standard:** Never soften criticism to protect ego. Never present guesses as facts. Never give generic advice that applies to everyone.

**Specificity Standard:** Every flaw must name the exact mechanism of failure. Every risk must include a contingency. Every recommendation must include the first physical action.

Q: Why publish an artifact instead of building a backend first?
A: Compute cost is billed to the end user, not you — free validation before infrastructure spend.

Q: Why does storage key design matter?
A: Combined keys avoid rate limits and lag; one object per logical unit beats five small calls.

Q: What's the real threshold where a tool becomes a business?
A: When someone would rather pay than lose access — not feature count.

Q: What's the #1 beginner mistake across Build, Ship, and Scale?
A: Doing more of the current stage instead of moving to the next one.

Q: Why describe the job, not the layout?
A: The job defines success criteria; the layout is just decoration.

Q: Why iterate only 3-5 times on one artifact?
A: Past that, diffs get messy and Claude contradicts earlier structure.

Q: Why test on mobile before finalizing?
A: Most traffic is mobile. Broken mobile experience kills conversion before it starts.

Q: Why real data before UI polish?
A: A beautiful UI with fake numbers proves nothing. A rough UI with real data proves the tool works.

Q: Why does one shipped integration beat three half-built ones?
A: A working integration that removes one manual step is a product moat. Three unfinished ones are technical debt.

Q: Why automate only after 5+ manual correct runs?
A: You can't automate a process you don't understand yet. Automating a broken process just breaks it faster.

Q: Why MRR over one-time sales at the start?
A: MRR compounds. One-time doesn't. At zero-budget-founder numbers, recurring revenue is survival.

Q: Why start with one price point, not three tiers?
A: Tiers are an optimization for segmentation. With zero paying users, there's nothing to segment yet.

Q: Why price to outcome, not build time?
A: A 20-minute build that saves 10 hours is worth more than a 2-month build that saves 10 minutes.

Q: Why is separating "content business" from "tools business" fatal?
A: Each tool is proof for the content. Each piece of content is the funnel for the tool. Separate them and both starve.

Q: Does `localStorage` work in a published Claude artifact?
A: No — the artifact sandbox blocks it silently. Use `window.storage` inside artifacts; `localStorage` is fine once deployed to real hosting (Tier 2/3).

Q: What's the difference between Claude Code artifacts and Chat artifacts?
A: Claude Code = Team/Enterprise only, org-only sharing, no public links. Chat = Free/Pro/Max, public publish links, `window.storage`. If you're on Free tier, you build Chat artifacts.

Q: What's the difference between Publish and Share?
A: Publish = public permanent link (Free/Pro/Max). Share = org-only (Team/Enterprise). Unpublishing is permanent — you cannot republish the same artifact.

Q: Why is annual pricing non-negotiable for zero-budget founders?
A: One annual payment = 12 months of runway. Cash upfront funds operations while you acquire more users.

Q: Why is the founder's lived debt story the best marketing asset?
A: $242,855.83 in debt → building tools to escape → teaching others. No competitor can replicate that transformation. Exact numbers build more belief than any face.

Q: What is the 3-hour window rule?
A: Hour 1 = build. Hour 2 = ship/distribute. Hour 3 = scale/optimize. No task crosses hour boundaries. Building bleeds into shipping = nothing ships.

Q: Why is "boring SaaS" the winning strategy in 2026?
A: A tax deduction calculator for landlords outperforms a generic AI assistant. Specific, unsexy tools for wealthy niches have higher retention and lower churn than flashy wrappers.

Q: What is the pre-sell validation rule?
A: Landing page + Loom demo + payment intent BEFORE code. <5 pre-orders in 7 days = kill the idea. Gil Hildebrand pre-sold $20K before writing code.

Q: Why is retention more important than acquisition for zero-budget founders?
A: Retaining 1 user is cheaper than acquiring 2. 70% of habit apps lose users in 30 days. Beat that number first.

Q: What is the aha moment and why does it matter?
A: The single action that makes users sticky. Push every user toward it within 60 seconds. For FreedomCalc: seeing the debt-free date. For ProposalForge: generating the first proposal.

Q: Why is white-labeling faster cash than individual MRR?
A: Agencies have existing client relationships. You don't need US credibility — they do. $497–$1,497 upfront vs. $49/month over 10 months.

Q: What is parallel entrepreneurship?
A: Connected ventures where audience, templates, and systems serve multiple products. FreedomCalc users become ProposalForge users become newsletter subscribers. Assets compound.

Q: Why is the artifact a capture, not an application?
A: Artifacts prove demand. They do not replace production infrastructure. Graduate to Tier 2/3 when metrics say so, not when ego says so.

Q: What is vibe coding and when should I use it?
A: Plain-language prompting → AI builds. Use for prototypes and MVPs. Speed over perfection. One-hour builds. Switch to structured coding only after validation.

Q: Why track AI costs per user?
A: $0.003/generation × 5,000 generations = $15. A power user can kill your margin. Cap costs, track usage, alert at 80% of budget.
